## Жизненный цикл репозитория
В качестве ЖЦ наша команда выбрала подход, схожий с XP (eXtreme Programming), но в контексте написания md-документа вместо кода. Для полноценного XP не хватает специфических инженерных практик: TDD, pair programming и т.д.

Заимствованные концепции XP:
- короткие циклы и малые выпуски
- частая интеграция
- коллективная ответственность за результат
- **периодическая** парная работа по некоторым пунктам

Другие ЖЦ не были выбраны, так как подходили хуже к условиям проекта и команды:
- каскадный ЖЦ больше подходит, когда работа чётко выстраивается в этапы. В данном проекте важно не потерять согласованность между пунктами, потому после "завершения этапов" всё равно придётся к ним часто возвращаться
- спиральный ЖЦ предлагает упор на анализ рисков на каждой итерации, что с учётом сжатых сроков будет избыточно
- V-модель предлагает более жёсткие требования к тестированию каждого этапа, но, опять же, в рамках сжатых сроков и малого количества встреч предпочтение отдаётся скорости разработки

## Контрольные точки и версии регламента

Рабочие изменения интегрируются в `main` по мере готовности через Pull Request. Команда проводит короткую еженедельную сверку статуса, связанных разделов и рисков срыва сроков.

Официальные версии регламента формируются в контрольные точки - в день каждой из контрольных встреч:

Версия считается выпущенной, когда соответствующее состояние находится в `main`, проверено командой и помечено Git-тегом. До финальной приёмки версии `0.x` являются промежуточными и могут изменяться. `v1.0.0` выпускается после завершения итоговой проверки. Подробнее правила нумерации описаны в [CONTRIBUTING.md](./CONTRIBUTING.md)
