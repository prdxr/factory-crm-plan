# Правила совместной работы

## Основной документ

Основной результат проекта - `Factory.md`.
`main` - общая интегрированная версия документа. Не вносите в неё непроверенные изменения напрямую.

## Порядок работы

1. Перед началом работы согласуйте задачу, ответственного и ожидаемый результат.
2. Создайте рабочую ветку от актуальной `main`.
3. Вносите изменения небольшими логическими частями и сохраняйте их отдельными коммитами.
4. По окончании работы откройте Pull Request в ветку `main`. В описании укажите:
   - что изменено;
   - какие пункты затронуты;
   - какие связанные разделы следует проверить.
5. Назначьте другого участника в качестве ревьюера:
    - координатору - ответственного за затронутую часть либо любого участника для валидации мета-веток;
    - исполнителям - аналитика;
    - аналитику - исполнителей затронутых правками разделов (см. распределение ролей в README).
6. Исправьте замечания при наличии и объедините изменения в `main` после проверки.
7. Задача считается выполненной после слияния в `main`.

## Имена веток

Используйте формат `<тип>/<раздел>-<краткое-описание>`, например:

### Типы веток
| Тип           | Описание                                                                      | Пример                            |
| :---:         | :---                                                                          | :---                              |
| docs          | Добавление или существенное изменение текста регламента                       | docs/02-pick-lifecycle            |
| fix           | Исправление фактиеческой ошибки, форматирования, несогласованности и т.д.     | fix/05-06-versioning-consistency  |
| meta          | Обновление мета-данных проекта: README, CONTRIBUTING, .gitignore и т.д.       | meta/readme-update-checklist      |

Создавайте ветку для конкретной задачи или связанного набора изменений, а не на весь проект. Ветки должны быть короткоживущими.

## Сообщения коммитов
В репозитории приняты правила, схожие с методологией [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), но типы переопределены в соответствии с областью задания.
Используйте формат:

`<тип>(<область>): <краткое описание>`

Типы:

| Тип           | Описание                                                                      | Пример                                                        |
| :---:         | :---                                                                          | :---                                                          |
| docs          | Добавление или существенное изменение текста регламента                       | docs(03): добавить подраздел об артефактах                    |
| fix           | Исправление фактиеческой ошибки, сломанного форматирования и т.д.             | fix(04): исправить именование веток фичей                     |
| meta          | Обновление мета-данных проекта: README, CONTRIBUTING, .gitignore и т.д.       | meta(readme): изменить распределение ролей                    |
| refactor      | Изменение стиля или перефразирование, не являющиеся исправлением ошибок       | refactor(09): заменить термин "деплой" на "развёртывание"     |
| consistency   | Исправление несогласованности между пунктами                                  | consistency(07): изменить частоту стресс-тестов 4 -> 2 недели |

Описание коммитов (кроме типа и области) следует писать на русском языке и начинать с глагола в начальной форме.

## Проверка изменений

Перед отправкой Pull Request проверьте:

- текст соответствует заданию и не противоречит уже согласованным решениям;
- названия ролей, артефактов и этапов согласованы с другими разделами;
- ссылки и перекрёстные ссылки работают;
- изменения не оставили устаревших формулировок в соседних разделах.

## Конфликты

Не разрешайте конфликт выбором "оставить только мою" или "оставить только чужую" без проверки. Сравните изменения, согласуйте итог с авторами затронутых разделов и после разрешения конфликта проверьте всю изменённую часть `Factory.md`.

## Формирование и выпуск версий

Изменения вливаются в `main` небольшими порциями через Pull Request. Наличие изменений в `main` само по себе не означает, что выпущена новая официальная версия регламента.

Перед каждым выпуском координатор:

1. Проверяет, что все запланированные к контрольной точке изменения влиты в `main`, а незавершённые задачи отмечены.
2. Организует сквозную проверку `Factory.md`: полнота обязательных разделов, единообразие терминов, согласованность перекрёстных ссылок и отсутствие противоречий.
3. Проверяет затронутые сопроводительные артефакты: README, CONTRIBUTING, чеклисты...
4. Создаёт Git-тег на проверенном коммите в `main` и публикует результат как выпуск репозитория.

### Критерии выпуска

Версию можно выпускать, если:

- все обязательные разделы, предусмотренные для этой контрольной точки, представлены в `Factory.md`;
- изменения прошли ревью и объединены в `main`;
- проверена согласованность затронутых разделов, в особенности связи раздела 3 с разделами 4–9;
- форматирование файла отображается корректно, нет поломанных элементов.

### Правила нумерации

- `v0.1.0`, `v0.2.0` - промежуточные версии до итоговой приёмки.
- `v1.0.0` - финальная согласованная версия регламента.
- После `v1.0.0` исправление опечаток или форматирования без изменения смысла увеличивает номер исправления: например, `v1.0.1`.
- Изменение содержания раздела без нарушения общей структуры увеличивает второй номер: например, `v1.1.0`.
- Несовместимое изменение ранее согласованных правил, требующее пересмотра связанных разделов, увеличивает первый номер: например, `v2.0.0`.
